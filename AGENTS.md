# Agent instructions

This file is for every AI agent that works in this repository, whatever its product or name.

## Read the shared instructions first

Before you start a task, read and follow the canonical instructions in the repository [suhancz/ai-agent-config](https://github.com/suhancz/ai-agent-config). Start with its root [AGENTS.md](https://github.com/suhancz/ai-agent-config/blob/main/AGENTS.md) and follow the policy links that apply.

## Rules of this repository

These rules add to the shared instructions; they do not replace them. If a rule here and a shared rule really conflict, do not decide alone: describe the conflict and ask the user.

- Check the CI first and fix what is red before you start new work. The test logs are on the `ci-results` branch (`test-users.log`, `test-role.log`, `test-unit.log`, `test-backups.log`, `test-backups-functional.log`), the Super-Linter log is `lint.log` on the `ci-lint-results` branch. Read the real logs.
- Whenever the linter fails on this repository, read [lint.log](https://github.com/suhancz/ansible-mailserver/blob/ci-lint-results/lint.log) on the `ci-lint-results` branch and fix the findings automatically, at their cause, on the same branch, without waiting to be asked. The first lines of the log state the result of the lint job, the linted commit (it must be the commit you pushed; otherwise the run is not finished or is an old one) and the event. The excerpt after them only shows the first 300 matching lines and warnings fill it, so look for errors and failures of every linter in the full log below it, and say so when the log you can read is truncated before the failure. Fix the finding itself; do not hide it with an ignore entry unless the owner decided that. Read the log again after every fix.
- Read [memory/MEMORY.md](memory/MEMORY.md) before you write: it holds the lessons from real linter outputs (for example the terms that the natural language linter rejects), notes on the tools and the decisions of the owner. Record every new lesson of this repository there, in the same commit as the change that taught it. This file and the memory file are kept after the Kolab release and go to `main` with it; only the status files (`TODO.md` and `todo/`) are deleted.
- High priority: every change of what the server does needs a CI test in the same commit (a new or extended test in `.github/workflows/tests.yml` or in the converge workflow). Check this every time before you prepare a commit: name the functionality the commit changes, and name the test that covers it. If no test covers it, add one; if that is not possible yet, say so in the commit message, add the gap to `todo/tests.md` and tell the user. Never hide a missing test.
- Order of the tests (owner, 2026-11-27): backup and restore tests against the full deployment happen only after a full deployment is possible. A full deployment is only possible once every other item of the status files is done, except the full deployment itself and the backup and restore tests. Until then keep the individual tests as they are (templates, name derivation, unit tests, syntax check, and the backup test with dummy services), and give every new change its own individual test.
- Keep the work status in the split format of the shared rule: the index `TODO.md` (goal, current state and revision, marks, open decisions, resume prompt, and before each category link the counts of its items done, in progress and to do, plus the overall counts of items and categories) and one file per task category in `todo/`. Update the touched files and the counts in every commit, close only items that a CI run verified, and delete `TODO.md` and `todo/` together in the last commit before the pull request is merged.
- Keep all AI-generated content small (owner, 2026-11-27; shared rule in `ai-agent-config`, section on small files, truncation-safe edits and split status files): as few words as possible with the same meaning, every file under 25 KB, split by topic with an index. The connector cuts large reads (a 32 KB file came back cut off, so 30 KB is the limit) and writes only whole files: read each file whole before editing (compare the listed size with what you received; read the rest from the raw URL at a commit SHA when cut off), never push a file built from a partial read, and check the size and the end of every pushed file.
- Run tests only in the CI containers (AlmaLinux 8, see `.github/workflows/tests.yml`). Add new tests there.
- Never pin the version of a tool, an action, a collection or a package. Always use the latest, and use the canonical (current) names of modules and collections.
- Scripts that have to be executable are listed in `.github/executable-files.txt`; add every new script there. Line endings are LF everywhere (`.gitattributes`). The lint workflow repairs both with a bot commit.
- When the owner gives a permanent instruction for this repository, add it to this file or to the status files in the same task, and keep your own memory of it where you have one.
- Name files after what they do.
- Explain changes in plain language and work independently; ask only when something is really unclear.
- Read `README.md` for the role variables and keep it current when behaviour changes.
